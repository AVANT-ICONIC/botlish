# Mutants of the hash-table experiment's separate-chaining implementation,
# impl/chain.bot (audit/hash-table/tools/mutate.tcl -file THIS; the format
# of tools/mutants.txt): each a deliberate bug of the kind the brief names
# (wrong bucket index, collision not checked, duplicate insert, resize
# loses an entry, probe terminates too early, load threshold off by one,
# equality omitted after a hash match) or of chaining's own invariants (the
# bucket rebuilt by a replacement or a removal, the count, growth's rehash
# and the insert that triggers it).
#
#   @@ NAME DESCRIPTION
#   ## impl/IMPL.bot
#   <<<<
#   text to replace (must occur exactly once in the file)
#   ====
#   replacement
#   >>>>
#
# The brief's kinds that are equivalent, or do not exist, in this
# representation, and what replaces them here:
#
#   * "wraparound broken": chaining has no probe sequence (a lookup examines
#     one bucket), so there is nothing to wrap. Not listed.
#   * "wrong bucket index" made consistently -- every operation using the
#     same wrong in-range home, e.g. `bit_and(h, cap - 2)` -- is equivalent
#     through the interface: any in-range function of the hash is a valid
#     (worse-distributed) home. Only the slots it fills differ, and the
#     interface does not expose them (`probes` is a diagnostic the fuzzer
#     does not check). The listed wrong-index mutants are inconsistent
#     between operations (lookups, the post-growth insert, growth's rehash)
#     or leave the range (`bit_and(h, cap)`, the power-of-two mask off by
#     one).
#   * "equality omitted after hash match" with the full stored 61-bit hash
#     is unobservable (tools/mutants.txt explains why: no two keys of one
#     kind with equal 61-bit hashes are known). Listed instead: a lookup
#     that trusts a match of the hashes' low 6 bits and omits the key
#     comparison, the bug of a table that stores a truncated hash -- killed
#     by the collide profiles, whose keys share their low hash bits.
#   * "compare the stored hash" omitted (key equality alone) is correct by
#     construction: it only costs time. Not listed.
#   * Growth walking the old buckets in another order is equivalent
#     outright: with doubling, new bucket k receives entries from old bucket
#     k mod cap only, so the walk order over old buckets never changes a
#     bucket. Not listed.
#   * The order of a bucket's entries (growth reversing each bucket, a
#     replacement moved to the bucket's end) changes only `probes` of single
#     keys, never a lookup's result, so it is equivalent through what the
#     fuzzer checks -- and through a probe sum over every key (a bucket of
#     length L contributes 1 + ... + L in any order). It is checked instead by
#     bench.bot's probes mode on a key subset (N 1024, M 100) against an
#     independent model of the bucket states; the reversed-growth edit is
#     caught there. Not listed.
#   * `from_lists` is not exercised by the trace driver; it is lpa's loop
#     over `put`, unchanged. Not mutated.

# Bucket index

@@ chain-lookup-wrong-bucket lookups scan the bucket after the key's home while inserts use the home (wrong bucket index)
## impl/chain.bot
<<<<
    t.buckets.at(home(h, slots(t)))
====
    t.buckets.at(home(h + 1, slots(t)))
>>>>

@@ chain-home-mask-off-by-one the home is bit_and(h, cap), not bit_and(h, cap - 1): an index outside the bucket array (wrong bucket index)
## impl/chain.bot
<<<<
    h.mod(cap)
====
    bit_and(h, cap)
>>>>
