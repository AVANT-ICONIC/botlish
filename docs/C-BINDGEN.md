# C-BINDGEN.md

Automatic C binding generation: `tools/c-bindgen.tcl` turns real C headers
into ordinary Botlish source -- `extern c library`, `extern c fn` with its
link symbol and its explicit pointer contract, opaque pointee types, typed
constants -- and into C thunks for the APIs that are macros or static inline
functions, with a deterministic report of every public name it bound and
why it did not bind the others.

> The generator may interrogate a C implementation. Botlish's compiler must
> not become one.

> Generate truthful bindings for the subset Botlish can express; classify
> the rest. Never approximate an unsupported C ABI into something that
> merely happens to compile.

What the generator emits is source a person could have written: it is
committed (`generated/c/PROFILE/TARGET/`), reviewed as a diff, compiled by
the ordinary front end like any application module (IMPORTS.md,
"Application modules"), lowered and linked by the ordinary C FFI (C-FFI.md).
The compiler never learns that a generator wrote it, and compiling a
program over a generated binding needs no header, no preprocessor and no C
compiler (`cb-fixture-no-c-at-compile-time`).

```botlish
# sdl3::video -- GENERATED by tools/c-bindgen.tcl (profile sdl3, target linux-x86_64):
# do not edit; regenerate with `tclsh9.0 tools/c-bindgen.tcl generate sdl3 -target linux-x86_64`.
# The constants and directly linked functions of include/SDL3/SDL_video.h (C-BINDGEN.md).
import ffi::c
import sdl3::ctypes

extern c library "SDL3"

# ... (an excerpt of generated/c/sdl3/linux-x86_64/sdl3/video.bot)
SDL_WINDOW_RESIZABLE = sdl3::ctypes::c_ulong(32)

# C: SDL_Window *SDL_CreateWindow(const char *title, int w, int h, SDL_WindowFlags flags)
extern c fn SDL_CreateWindow(
    title: ffi::c::Ptr[ffi::c::Char] read noescape,
    w: ffi::c::Int,
    h: ffi::c::Int,
    flags: ffi::c::ULong
) -> ffi::c::Ptr[sdl3::ctypes::SDL_Window] independent
```

## 2. Pipeline

```
profile (tools/c-bindgen/profiles/NAME.tcl) + target
   |  ::chdr::toolchain::configFor TARGET      clang --target=TRIPLE (the target's own system headers)
   v
preprocess the entry headers; preprocess again with -dD   (tools/cheader/pipeline.tcl)
   |  ::cdecl::parse                         records: function typedef struct enum variable
   |  macro records, each expanded by the preprocessor once
   v
candidates (model.tcl)        every public name classified: direct, alias, thunk, excluded, unsupported
   |                          and the questions for the compiler (typedef and enum types, constants, symbols)
   v
ABI probe, symbol probe (probe.tcl)   one translation unit each, compiled to assembly, read back
   v
resolve (model.tcl)           signatures, link symbols, manual contracts, constants, identities
   v
thunks (generate.tcl)         the shim compiled once; a thunk the compiler rejects becomes unsupported;
   |                          with evidence llvm, its -O2 LLVM IR's attributes become proven facts
   v
emit (emit.tcl, report.tcl)   modules, ctypes, thunk modules, shim.c, manifest.txt, report.txt, report.tsv
```

`::cbind::generate::run PROFILE TARGET` returns `{files FILES model MODEL
timing TIMING}`: the files as a dict path -> text, and the model, which
holds every stage's data (the records, the classified APIs, the probe
facts, the identities, the constants). Nothing in the generator parses C
beyond the archaeology's declaration parser or interprets a macro beyond
classifying its expansion's tokens; every value, type and symbol is the
compiler's answer to a question.

The toolchain is the target's: `configFor` maps a Botlish target to a
clang triple (`x86_64-linux-gnu`, `aarch64-linux-gnu`, `arm64-apple-macos11`,
...), with `BOTLISH_C_CC` (clang by default) and an optional sysroot
(`BOTLISH_C_SYSROOT_<TARGET>` with the target's `-` spelled `_`, such as
`BOTLISH_C_SYSROOT_macos_aarch64`, or `BOTLISH_C_SYSROOT`). A target's system
headers are its own or none: generating for macOS off a Mac without an SDK
is an error, because clang would otherwise fall back to the host's
`/usr/include` and preprocess Linux's headers as if they were Apple's.

## 3. Profiles

A profile is a Tcl file that evaluates to a dict (`tools/c-bindgen/profile.tcl`
validates it):

| key | meaning |
|---|---|
| `name` | the binding's root namespace (`tcl`, `boringssl`, `sdl3`, `bgf`) |
| `headers` | a header profile in the archaeology's format: `library`, `source` (`{url URL tag TAG commit COMMIT}` or `{local DIR}`), `includeDirs`, `defines`, `undefines`, `flags`, `public` (the globs of public headers), `entry`; optional `targetDefines` |
| `targets` | the Botlish targets it supports (`core/cabi.tcl`'s names) |
| `modules` | `{stripPrefix P}`: a header's module is its file stem without P, lowercased |
| `libraries` | rules `{headers GLOBS targets GLOBS names {LIB ...}}`: each module declares every matching rule's libraries, in rule order |
| `exclude` | explicit deny patterns of API names |
| `contracts` | `{FUNCTION {PARAM FACTS ... result FACTS}}`: the binding author's foreign contracts |
| `groups` | one contract stated for an explicit list of functions |
| `thunks` | `{NAME {C PROTOTYPE}}`: the signature of a function-like macro API to thunk |
| `stubs` | `thunk` or `unsupported`: what a stub-table redirection becomes |
| `evidence` | `none` or `llvm` (section 13) |
| `output` | where the bindings are committed (default `generated/c/NAME`) |

Every policy is checked against the headers: a contract naming a function
the target's headers do not declare, a parameter the function does not
have, a group naming a missing function, a thunk signature of no macro or of
a declared function -- each is an error, never a silent no-op
(`cb-policy-stale`); a fact a declaration cannot carry (a contract on an
`int`, a provenance on a parameter) is the profile's error
(`cb-policy-facts`).

Tcl's and BoringSSL's profiles reuse the archaeology's header profiles as
they are (`tcl-embed`, `boringssl-static` with the acceptance's
`BORINGSSL_PREFIX`), so the generator's inventory is the archaeology's
(section 26).

## 4. The command line

```sh
tclsh9.0 tools/c-bindgen.tcl profiles
tclsh9.0 tools/c-bindgen.tcl fetch PROFILE                        # the pinned sources, into Botlish's cache
tclsh9.0 tools/c-bindgen.tcl generate PROFILE ?-target T|all? ?-out DIR? ?-timing 1?
tclsh9.0 tools/c-bindgen.tcl check PROFILE ?-target T|all|committed? ?-dir DIR?
tclsh9.0 tools/c-bindgen.tcl report PROFILE ?-target T? ?-why NAME? ?-status S? ?-reason R?
tclsh9.0 tools/c-bindgen.tcl build PROFILE ?-target T? -out DIR   # the shim's static library
tclsh9.0 tools/c-bindgen.tcl stage PROFILE ?-target T? -app DIR -into DIR
tclsh9.0 tools/c-bindgen.tcl run PROFILE ?-target T? PROGRAM.bot ?MAIN.TCL OPTIONS...?
tclsh9.0 tools/c-bindgen.tcl diff PROFILE ?-targets {A B}?        # what differs between targets
```

`run` stages the program's directory beside the committed binding (one
application root), builds the shim and runs `main.tcl` on it: the program
is compiled by the ordinary compiler, from ordinary modules. The fixture's
profile file is `fixture.tcl` and its namespace `bgf`; the command line
names a profile by its file.

`report -why NAME` answers from the committed `report.tsv`:

```
$ tclsh9.0 tools/c-bindgen.tcl report fixture -target linux-x86_64 -why bgf_scale
function bgf_scale: not generated (unsupported): double,float
  parameter 1 (x): double
  parameter 2 (y): float
  result: double
```

## 5. ABI probes

The C compiler answers every question about types and values, in one
batched translation unit per question, compiled **to assembly** and read
back -- nothing is linked or run, so every target is probed the same way
from any host (the archaeology's probe ran a native program):

```c
const unsigned long long botlish_probe_7[] = { (unsigned long long)(sizeof(bgf_u64)),
    (unsigned long long)(_Generic(((bgf_u64)0), char: 1, signed char: 2, ..., _Bool: 12,
                                  float: 13, double: 14, long double: 15, default: 0)) };
```

The data directives (`.quad`, `.xword`, `.8byte`, `.dword`, `.zero`) are
the values. A relocated word (an address the linker places) is reported as
such, never read as an integer (`BN_DEC_FMT1`, a string, is no integer
constant). An entry the compiler rejects is dropped with the compiler's
message and the rest compiled again, so one bad macro never hides the
others.

Asked: every typedef on the chain of every type a bound signature mentions
(`td:NAME`: its size and the C integer type `_Generic` selects), every enum
(`enum:TAG`), every enumerator's value, and every object-like macro the
classifier calls a constant (its type code and value).

## 6. Link symbols

The link symbol of a direct API is the compiler's:

```c
void (*const botlish_sym_3)(void) = (void (*)(void))&(bgf_labeled);
```

compiled to assembly; the relocation's target, minus the target's user
label prefix (`__USER_LABEL_PREFIX__`, `_` on Apple targets), is the
symbol. So an asm label (`bgf_labeled_v2`), a `#pragma redefine_extname`
(`bgf_renamed_impl`; BoringSSL's whole prefixed build,
`botlish_bssl_SHA256`), and an object-like macro alias (`#define
bgf_legacy bgf_current`) all come out of one rule for every name alike: no
name is special and no prefix is spelled in the generator. A symbol without
the target's label prefix (an asm label that bypasses it) has no C-level
name and is unsupported. An API name that is no link-time constant (a
stub-table member) is a compile error the probe records.

When the symbol differs from the Botlish name, the extern says so: `extern c
fn bgf_labeled named "bgf_labeled_v2"(x: ffi::c::Int) -> ffi::c::Int`.

## 7. Classification

Every public declaration and every public macro is one row of the report.
An API name is:

| kind | when | what is emitted |
|---|---|---|
| direct | a declared, non-inline function whose name is not also a macro (or is a macro naming itself) | an extern of the symbol the probe found |
| alias | an object-like macro naming a function (`#define bgf_legacy bgf_current`), a renaming function-like macro (`#define bgf_call_add(a, b) bgf_add(a, b)`) | an extern of the target function's symbol with its signature, `named` |
| thunk | a static inline function; a declared function shadowed by a function-like macro of its name; a stub-table redirection (profile `stubs thunk`); a macro the profile gives a signature | an extern of the shim's C wrapper (section 14) |
| excluded | the profile's `exclude` | nothing; the row says so |
| unsupported | anything else, with every blocker found | nothing; the row names each blocker |

The blockers: `float`, `double`, `long-double`, `complex`,
`by-value-aggregate`, `union-by-value`, `variadic`, `va-list`,
`no-prototype`, `unsupported-calling-convention`,
`unsupported-callback-signature`, `typedef-abi-mismatch`,
`enum-unknown-abi`, `unresolved-typedef`, `unsupported-type`,
`unsupported-bool` (with `-bool 0`), `no-link-symbol`, `stub-redirect`,
`thunk-rejected`, `macro-needs-signature`, `unsupported-macro`. An API may
have several; each is located ("parameter 2 (y): float"), and all are
reported, not only the first, so the report can say which missing
capability each API waits for.

A declaration redeclared with a different type is a generator error.

## 8. Macros

A macro is what the preprocessor makes of it: the archaeology's classifier
(`tools/cheader/macrocat.tcl`) reads the expansion's tokens and names its
shape -- an integer literal, an integer expression, an expression with
casts, a string, a type spelling, a decoration, an alias of a function or
an object, a call wrapper, a statement, a fragment. The generator then
decides by shape and by the compiler's answer:

* an object-like constant: asked of the ABI probe; a constant when the
  compiler gives it an integer type (section 11), else reported (a double, a
  pointer, an address);
* an object-like alias of a function: an alias (section 7);
* a function-like macro renaming a function: an alias; otherwise a thunk
  when the profile states its signature (`Tcl_Eval`), else unsupported:
  `macro-needs-signature` when it computes or calls something, else
  `unsupported-macro`;
* strings, empty macros, decorations, type spellings, fragments: reported as
  not constants, with their shape.

A declared function shadowed by a function-like macro of its name
(`#define Tcl_DecrRefCount(objPtr) ...` beside a declaration) is thunked:
a C caller of the name gets the macro, so the binding calls the macro too,
from a thunk with the declaration's signature. Only a macro that expands to
a call of its own name is the declaration (bound directly).

## 9. Declaration mapping

| C | Botlish | how |
|---|---|---|
| integer types | `ffi::c::Char` ... `ffi::c::ULongLong` | the parser's canonical spelling |
| a typedef of an integer type (`uint64_t`, `size_t`, `Tcl_Size`, `SDL_WindowFlags`) | the scalar its chain ends in on the target | resolved through every typedef, then confirmed by the compiler's `_Generic` of the typedef itself: a typedef an attribute widens (`mode(TI)`) is `typedef-abi-mismatch`, never the declared type. No nominal type per typedef (C-HEADER-ARCHAEOLOGY.md item 63) |
| an enum (by tag or typedef) | the scalar the compiler gives `enum T` | `enum bgf_color` with enumerators 0, 5, 6 is `unsigned int` on clang, so `ffi::c::UInt` |
| `_Bool` | `ffi::c::Bool` | section 16 |
| `T *` | `ffi::c::Ptr[T']` | any depth; `void *` is `Ptr[ffi::c::Void]` |
| `struct T *`, `union T *` | `ffi::c::Ptr[NS::ctypes::T]` | section 10 |
| a function pointer, a parameter of function type | `ffi::c::FnPtr[Fn{args: [...], return: R}]` | every argument and the result mapped; a variadic or unprototyped callback, or one with a double, is `unsupported-callback-signature` |
| an array parameter (`unsigned char out[4]`) | the pointer it decays to | as C adjusts it |
| `void` result | `unit` | |
| a C name that is a Botlish keyword | renamed (`fn_`, `type_`, `loop_`), `named` keeps the symbol | |
| an unnamed parameter | `arg1`, `arg2`, ... | |

## 10. Opaque types

One pointee identity per C tag, never `Ptr[Void]`: `struct bgf_handle` is
`bgf::ctypes::bgf_handle`, `struct SDL_Window` is `sdl3::ctypes::SDL_Window`.
The identity is named by the first typedef naming the tag directly
(`typedef struct bgf_window_ bgf_window` gives `bgf_window`), else by its
tag. Every identity lives in one canonical owner, the binding's `ctypes`
module, declared once however many modules point to it (the fixture's
`bgf_handle` is pointed to by functions of two headers), and imported by the
modules that use it:

```botlish
# struct bgf_handle
opaque struct bgf_handle:
    tag: unit
```

The type is opaque even when the C struct is complete (`bgf_point`,
"a complete C type seen through pointers only"): no field is generated, no
layout is claimed, and the report counts such signatures as needing memory
views (section 37). Two tags whose names collide stay two types: the
fixture's `typedef struct bgf_other bgf_twin;` beside a tag `struct
bgf_twin` gives `bgf_twin` and `bgf_twin_struct` (`cb-fixture-mapping`).
Identity is keyed by the C tag (`struct NAME`), never by a spelling.

## 11. Constants

A constant is the compiler's value of the compiler's C type:

| C | type | value |
|---|---|---|
| `#define BGF_FLAG_A 0x00000001u` | `unsigned int` | `bgf::ctypes::c_uint(1)` |
| `#define BGF_BIG UINT64_C(0xFFFFFFFFFFFFFFFF)` | `unsigned long` on LP64 Linux, `unsigned long long` on Apple | `c_ulong(18446744073709551615)` |
| `#define BGF_SIZE_NONE ((bgf_size)-1)` | `long` (the typedef's) | `c_long(-1)` |
| `#define BGF_CHAR 'x'` | `int` (a character constant is an int in C) | `c_int(120)` |
| `#define BGF_HIGH_CHAR ((char)200)` | `char` | `c_char(-56)` where plain char is signed, `c_char(200)` on AArch64 Linux |
| `BGF_BLUE` (an enumerator of `enum bgf_color`) | the enum's type, `unsigned int` | `c_uint(6)` |
| an anonymous enum's enumerator | `int` | |

The converters (`fn c_uint(value: ffi::c::UInt) -> ffi::c::UInt`) live in
`ctypes`: a module binding is a typed constant through an ordinary function
whose declared result is the scalar, checked like any result
(ELIMINATE-AUTOMATIC-TYPE-PREDICATES.md: no type is callable). A `_Bool`
constant is `true` or `false`. Floating, string, pointer, address and
fragment macros are reported, never emitted.

## 12. Contracts

A pointer parameter's facts are `access` (read, write, unknown) and
`escape` (declared noescape, proven noescape, captures, unknown); a pointer
result's provenance (independent, alias of a parameter, unknown). C-FFI.md
section 4 says what each admits. The generator's rule:

* **Unknown by default.** No fact comes from a C type, a parameter name, a
  function name or a namespace. `const` is no fact: `const char *` says
  nothing about escape (`bgf_point_sum(const bgf_point *)` is emitted with
  no fact, `cb-fixture-contracts`). An unknown escape retains, so a call
  passing a pointer there is direct authority at its call site
  (DIRECT-MODULES.md) and admits no byte exposure.
* **Manual facts** come from the profile (`contracts`, `groups`) and are
  emitted as the binding author's declarations: `read noescape`, `write
  noescape`, `independent`, `alias out`.
* **Proven facts** come from the compiler's IR of the shim (section 13) and
  are emitted as `proven noescape`, never as the author's `noescape`.
* **Conflicts fail.** The profile's `write` where the compiler proves
  `readonly`, its `captures` where it proves `nocapture`, its provenance
  where the compiler proves another `returned` parameter: generation stops
  naming both sources (`cb-policy-conflict`). A compiler fact that agrees
  is recorded beside the manual one.
* **Every favorable fact's source is in the manifest**: `contract
  bgf_digest out {access write escape declared-noescape} manual {contract
  bgf_digest}`, `contract bgf_point_x p {escape proven-noescape access
  read} compiler {nocapture readonly}`.

A written parameter's bytes come back as a field of its name beside
`result` (C-FFI.md section 6); a parameter named `result` is renamed.

## 13. Compiler evidence

With `evidence llvm`, the shim (section 14) is compiled once more by clang
to `-O2` LLVM IR, and each thunk's own parameter attributes are read:
`nocapture` (and LLVM 21's `captures(none)`), `readonly`, `writeonly`,
`readnone`, `returned`. The thunk calls the real API, so what the optimizer
proves of the thunk's parameter it proved through the API's visible body --
which exists only for inline functions and macros; a declared function's
body is in another translation unit and proves nothing. The facts become
`proven noescape`, `read`, `write` and `alias P` (an alias only when the
result and the parameter have the same Botlish type). The IR's producer
line is recorded in the manifest (`evidence llvm {Ubuntu clang version
18.1.3 (1ubuntu1)}`).

Measured: 8 proven parameters in Tcl, 123 in BoringSSL, 16 in SDL3 (the
inline functions' pointer parameters the optimizer could see through).

## 14. Thunks

A thunk is a C function with exactly the C signature of an API that has no
link symbol of its own, calling that API by its name:

```c
int botlish_bgf_bgf_point_x(const bgf_point *botlish_p) {
    return bgf_point_x(botlish_p);
}
```

Thunk symbols are profile-qualified (`botlish_PROFILE_NAME`), so one name in
two libraries' bindings never collides. All of a profile's thunks for one
target are one translation unit, `shim.c`, including the profile's entry
headers with its defines, compiled once by generation with
`-Werror=incompatible-pointer-types -Werror=int-conversion
-Werror=implicit-function-declaration -Werror=return-type`: a thunk the
compiler rejects becomes `thunk-rejected` with the compiler's message
(Tcl's `Tcl_InitStubs` macro takes another number of arguments than its
declaration; `Tcl_DumpActiveMemory`'s macro expands to nothing a non-void
function can return), and the rest compiles again.

`tools/c-bindgen.tcl build PROFILE -out DIR` compiles the committed
`shim.c` into one static library, `libbotlish_shim_NS_CRC.a`, whose name is
the CRC-32 of the shim's own text: a changed shim is a different library,
never a stale one. A thunk module declares the shim library and then the C
library (`extern c library "botlish_shim_bgf_143debf5"`, `extern c library
"bgf"`), so linking it pulls both; a program links only the libraries of
the modules it imports and only the externs it calls reach its foreign table
(`cb-fixture-only-reached-externs`).

Thunks are how the bindings reach 817 BoringSSL static inline functions
(the `sk_*` and `lh_*` families, `ERR_GET_LIB`), 13 SDL3 ones
(`SDL_MostSignificantBitIndex32`, `SDL_HasExactlyOneBitSet32`, ...), Tcl's
macro-shadowed functions (`Tcl_DecrRefCount`, ...) and Tcl's `Tcl_Eval`
macro. Each kind is checked against C: the thunk's results equal a C
caller's (`cb-tcl-thunk-behavior`, `cb-boringssl-thunk-behavior`,
`cb-sdl3-thunk-behavior`, the fixture's demo).

## 15. Tcl stubs

With `USE_TCL_STUBS`, `tclDecls.h` defines `#define Tcl_X
(tclStubsPtr->tcl_X)` for nearly every API: the name is a member of a
global table, not a symbol, and a binding that linked `Tcl_X` directly would
call another function than the one a C caller calls (or fail to link
against a stubs library). The generator never treats such a name as a
symbol: the classifier recognizes the table member, and the profile's
`stubs` policy makes it a thunk (the C call goes through the table) or
unsupported (`stub-redirect`).

Two profiles bind Tcl: `tcl` is the direct-link embedding configuration
(the archaeology's `tcl-embed`: no `USE_TCL_STUBS`, so no redirection exists
and every declared function is libtcl9.0's symbol), and `tclstubs` is the
stubs configuration (the archaeology's `tcl-stubs`), where 676 of its 694
redirected names are thunks through the table, 18 are unsupported (each
with its signature's or its thunk's blocker), and none is a direct extern (`cb-tcl-inventory`). The fixture's `bgf_get`
is the same pattern in one line: its implementation defines a same-named
function that returns another value than the table's, so a binding that
linked `bgf_get` directly would compute the wrong result in the demo.

## 16. C bool

SDL3 uses C `_Bool` (`bool` of `<stdbool.h>`) in 506 of its 1,405 API names:
nearly every function that reports success. Without it, a third of SDL3
could not be bound. The milestone adds one primitive, `ffi::c::Bool`, and
no other ABI expansion:

* `ffi::c::Bool` is Botlish's `bool` as a C type: a parameter takes `true`
  or `false`, a result is one; an `Int` is no bool. It may be a pointee
  (`Ptr[ffi::c::Bool]`) and appear in a function pointer's signature
  (hir/cabi.tcl, hir/types.tcl, hir/foreign.tcl).
* Its ABI class is `bool`: one byte, 0 or 1, zero-extended like an
  `unsigned char` (on x86-64 to the register's 32 low bits, as GCC and Clang
  callees read it). Natively it lowers to `i8 uext` in the platform C
  signature (native/src/codegen/clif.rs).
* A result byte that is neither 0 nor 1 is no `_Bool` a C compiler returns:
  a `NATIVE BOOL` failure naming the function and the byte, never a bool
  made of one bit (native/src/runtime/ffi.rs).
* The differential fixtures (tests/cffi/fixture.c) check it against C:
  round trips, what C sees of an argument in a register and on the stack,
  C's own `true` and `false`, a result register with dirty bits above the
  byte, the invalid byte (`cf-bool-type`, `cf-bool-transport`,
  `cf-bool-register`, `cf-bool-invalid`, `cf-bool-pointers`,
  `cf-bool-lowering`). The C FFI's and the C ABI types' fuzzers draw it.

C-FFI.md section 3 and C-ABI-TYPES.md record it. `-bool 0` generates as if
it did not exist (every `_Bool` an `unsupported-bool` blocker), which is how
the report counts what it unlocked: 456 SDL3 APIs are bound only because of
it.

Per profile and target, under `OUTPUT/TARGET/`:

## 20. Determinism and the check mode

Generation is a function of the profile, the target, the pinned headers
and the toolchain: two runs, another working directory, another time zone
and another locale give the same bytes, and no time, temporary path or host
path is in any file (`cb-fixture-deterministic`). Everything is emitted in
translation-unit order (declarations) and definition order (macros);
nothing iterates a hash or a directory; a system header's location is
written as "(a system header)", never its host path.

`check PROFILE -target T|all|committed` regenerates into memory and
compares byte for byte with what is committed: a difference is an exit 1
with each differing file's first differing lines and the coverage change
(`+ function bgf_added: direct`, `- function bgf_plain_char: was direct`,
`~ macro BGF_VERSION_MAJOR: ...`). A header update is therefore a generated
diff a reviewer reads (`cb-version-drift`), and the shim, whose thunks did
not change, is unchanged.

## 26. The archaeology's inventory, compared

The generator reads the archaeology's header profiles with the archaeology's
parser, so its inventory is the archaeology's: Tcl (`tcl-embed`) 753
declared functions and 1 static inline, BoringSSL 3,109 declared and 817
static inline, 2,867 BoringSSL integer-literal constants -- the same numbers
(`cb-tcl-inventory`, `cb-boringssl-inventory`; C-HEADER-ARCHAEOLOGY.md
items 20 and 63).

The archaeology estimated the simple-callable subset -- integer scalars and
pointers, no varargs, no aggregates by value -- at 2,929 of 3,109 BoringSSL
functions (94%) and 675 of 753 Tcl ones (90%) without callbacks, and 3,092
(99.5%) and 737 (97.9%) with static callbacks. Callbacks are ordinary
`FnPtr` values here (passed, never called from Botlish), so the second
figure is the comparable one:

| | archaeology (estimate, with callbacks) | generated |
|---|---:|---:|
| BoringSSL declared functions bound | 3,092 of 3,109 (99.5%) | 3,098 of 3,109 (99.6%) |
| BoringSSL static inline functions bound | not counted (no thunks) | 817 of 817 |
| Tcl declared functions bound | 737 of 753 (97.9%) | 732 of 753 (97.2%): 720 direct, 12 through the macro that shadows them |

The differences are exact. BoringSSL: the estimate left out the 9
functions whose callbacks take callbacks (C-HEADER-ARCHAEOLOGY.md item 66),
which the generator binds (a callback is a pointer value here, which
nothing calls), and counted the 3 `CRYPTO_poly1305_*` functions, which take
a pointer to an array (`uint8_t (*)[512]`) and have no `Ptr` form here:
3,092 + 9 - 3 = 3,098. Tcl: the generator binds the one callback-taking-a-
callback function too, and refuses 6 the estimate counted -- the 4 that take
a `double *` (no floating pointee) and the 2 macro-shadowed declarations
whose thunks the compiler rejects (`Tcl_InitStubs`, `Tcl_DumpActiveMemory`):
737 + 1 - 6 = 732.

## 27. The compiler's side

Nothing in `core/`, `hir/`, `surface/`, `compiler/` or `native/` loads the
generator or the C header library, and nothing in the compiler knows that a
module was generated. What the compiler gained is `ffi::c::Bool` (section
16), nothing else. The generated bindings go through every existing
discipline as ordinary application modules:

* **only reached externs**: a program's foreign table holds the C functions
  it calls, its link plan each library once (`cb-fixture-only-reached-externs`;
  the SDL3 acceptance's 16 functions of 1,102 declared);
* **HIR interchange**: a program over a generated binding written as
  `.hirx` and run by a fresh process, with no header, generator input or
  binding module left, behaves identically (`cb-fixture-interchange`);
* **the front-end cache** keys the binding modules like any imported module;
* **compilation isolation**: two bindings with the same Botlish names and
  other symbols, compiled one after the other, keep their own foreign
  declarations (`cb-fixture-isolation`);
* **static compile**: a `static compile:` block over a generated extern is
  decided like any block (`compiler::DiagnosticCode::Arity`, `Type`;
  `cb-fixture-static-compile`);
* **no C at compile time**: a child process with no compiler on its `PATH`
  and no header sources compiles a program over a generated binding
  (`cb-fixture-no-c-at-compile-time`);
* **directness**: a generated module is ordinary; its unknown escapes make
  its callers' calls direct edges (DIRECT-MODULES.md).

## 34. Not here, and what remains

* **macOS.** The generator is target-aware for `macos-aarch64` (the
  triple, the SDK sysroot, the `_` label prefix, Apple's typedef chains and
  char signedness), and the fixture's macOS binding is generated and pinned.
  The Tcl, BoringSSL and SDL3 macOS bindings need the macOS SDK's headers
  (`BOTLISH_C_SYSROOT_macos_aarch64`, or a Mac), which this environment does
  not have, and running anything on macOS needs a macOS port of the native
  backend, which this tree does not have. So no macOS binding of a real
  library is committed and no macOS acceptance has run. On a Mac with the
  SDK: `tclsh9.0 tools/c-bindgen.tcl generate sdl3 -target macos-aarch64`.
* **Calling an `FnPtr`, callbacks into Botlish**: 50 Tcl, 452 BoringSSL and
  36 SDL3 bound functions take a callback, which can be passed along (a C
  function pointer from C) but not made from a Botlish function.
* **Memory views**: 454 Tcl, 1,317 BoringSSL and 225 SDL3 bound functions
  point to a complete C struct the binding only knows as an opaque identity.
* **Floats** (SDL3: 114 API names), aggregates by value (8), varargs (23):
  their own milestones.
* **Macro signatures**: 63 Tcl, 66 BoringSSL and 113 SDL3 function-like
  macros compute something and have no signature of their own; each needs a
  profile signature to be thunked.
* **C strings**: every `const char *` result is an opaque `Ptr[Char]`.
* **Contracts at scale**: 98% of pointer parameters are unknown (section 29).
* A Windows target, a GCC evidence producer.

## 35. What to run when changing this

If you change the generator (`tools/c-bindgen/`), the C header library
(`tools/cheader/`), a profile or the fixture, run `tclsh9.0
tests/c-bindgen.test`, `tools/c-bindgen.tcl check PROFILE -target committed`
for every profile (regenerate and review the diff when it is intended),
`audit/c-bindgen/tools/fuzz.tcl` (several seeds) and
`audit/c-bindgen/tools/mutate.tcl` (every mutant in its `mutants.txt` must
still apply and be killed, by a test of behavior or the fuzzer: update a
mutant's text when you change the code it mutates, keeping it a mutant of
the same rule). A change to `tools/cheader/` also runs the archaeology's
`audit/c-header/tests/parser.test`, `tests/corpus.test` and
`tools/all.tcl` (its results must not change). A change to `ffi::c::Bool`
runs the C FFI's harnesses (C-FFI.md section 27).
